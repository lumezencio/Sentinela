# Fase 4B — Operação (TOTP, backup, atualização, imagens): plano de implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** o Sentinela passa a resistir a senha vazada (TOTP com códigos de recuperação), faz backup diário e restaura, atualiza com volta automática, e é instalado por imagens `amd64`/`arm64` assinadas e com SBOM, com o pipeline de segurança ampliado, terminando em `v0.4.0`.

**Architecture:** o TOTP é um segundo passo do login (`api/auth.py`) com token intermediário sem estado (HMAC, 5 min, cookie próprio); a sessão restrita do administrador é calculada a cada requisição (política em `config` + "tem TOTP?"), sem coluna nova em `sessao`. O backup vive num pacote `core/sentinela/backup/` (funções síncronas sobre `sqlite3.Connection.backup`, serviço assíncrono com agenda 03:00 no fuso) e é operado por CLI dentro do container; `backup.sh`, `restore.sh` e `update.sh` só orquestram `docker compose` do projeto `sentinela` por essa CLI. As imagens saem de `release.yml` (tag `v*`): candidata → trivy → promoção → cosign sem chave → SBOM; `install.sh`/`update.sh` consomem `IMAGENS=publicadas|locais` do `.env`.

**Tech Stack:** Python 3.12, FastAPI, SQLAlchemy 2 async, Alembic, `pyotp` 2.10.0, `segno` 1.6.6, `sqlite3` da biblioteca padrão; front HTML/JS sem framework (login e `seguranca.html` em JS puro, Configurações em Alpine CSP); bash (`set -euo pipefail`), Docker Compose 2.24.4+, GitHub Actions, cosign, trivy, CodeQL, Dependabot.

**Spec:** `docs/superpowers/specs/2026-11-18-fase4-operacao-design.md` — este plano cobre §6 inteiro (6.2 sem o `SENTINELA_FUSO`, já feito em 4A), §8 (parte 4B: `usuario.totp_cifrado`, `usuario.totp_ultimo_contador`, `codigo_recuperacao`), §9 (parte 4B) e §10. Fase anterior: `docs/superpowers/plans/2026-11-18-fase4a-alertas-telao.md` (concluída; a migração dela é a `0004`, esta é a `0005`).

## Review Focus

1. Duas requisições simultâneas com o **mesmo** código TOTP (ou o mesmo código de recuperação) → só uma cria sessão; a outra recebe 401 genérico (atualização atômica `WHERE totp_ultimo_contador < :c` / `WHERE usado_em IS NULL`). (Tasks 1 e 2)
2. Restaurar sobre um banco que deixou `sentinela.db-wal`/`-shm` para trás, e backup (tar) com membro `../x`, caminho absoluto, link simbólico, membro extra ou tamanho declarado diferente → o WAL velho nunca é reaplicado e o arquivo hostil é recusado sem extrair nada. (Task 3)
3. Disco cheio ou falha no meio do backup → nenhum arquivo parcial e nenhuma cópia boa apagada (a rotação só roda depois de o novo backup estar completo e verificado). (Task 3)
4. Restauração numa máquina com outra `SENTINELA_CHAVE_CREDENCIAIS` (o cenário do aviso do `.env`) → o core sobe; fontes e Telegram aparecem como "credencial ilegível, informe de novo", nunca erro 500 nem laço parado. (Tasks 3 e 4)
5. `update.sh` interrompido (Ctrl-C/SIGTERM) no meio, executado com árvore git suja ou com outra atualização em curso → o primeiro volta ao estado anterior, os outros recusam antes de tocar em qualquer coisa. (Task 6)
